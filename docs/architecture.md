# Архитектура NaviDnD

Windows-приложение для ролевой игры с ИИ-мастером. Правила D&D 5e задаются промптами; движок отвечает за состояние, геометрию, отображение и взаимодействие с игроком.

## Анимации интерфейса

`AnimationLoop` обновляет независимые анимации по монотонным часам. У каждого кадра своя длительность: кубик сохраняет паузу после каждого кадра (`catchUp: false`) и стартует после запуска звука; текст — режим `catchUp: false` с паузой 40 мс после символа, чтобы после задержки не печатать накопившиеся символы рывком. `Start` регистрирует параллельные анимации, `PlayAsync` ожидает последовательность, `DelayAsync` обновляет анимации и опрашивает ввод. Обработчики кадров выполняются синхронно из `Tick`: нельзя запускать фоновые записи в консоль или блокировать обработчик ожиданием ввода. Регистрацию нужно освобождать при закрытии экрана.

Диалог использует общий цикл для текста, спиннера, кубика и движения. Спиннер обновляет только нижнюю область; диалог пропускает неизменившиеся строки. Перетаскивание карты и окна обрабатывается при опросе ввода, без вложенных блокирующих циклов. Движения мыши объединяются в один кадр; при перетаскивании обновляется только поле карты, легенда — после отпускания. `AnsiColorRuns` сокращает повторные команды цвета в буфере карты. Порядок применения игровых патчей сохраняется.

`ConsoleRegionBuffer` хранит отдельные кэши строк текста и картинки; наведение обновляет только затронутые клетки, легенду и картинку. `SvgToBrailleConverter.PrepareAsync` готовит изображения в фоне; применение и вывод остаются в UI-цикле. Достижимость клеток для пути под курсором кэшируется до изменения состояния карты или героя.

## Игровой поток

`Program` загружает настройки, создаёт каталоги хранения и собирает `Storage`, `GameAiClient` и экраны. `MapScreenLoop` обрабатывает игру; `MovementHandler` выполняет движение и обнаруживает триггеры. Обычная ходьба не требует вызова модели.

`GameAiClient` выбирает промпт действия и контекст из `AiContextBuilder`. `SwitchableAiProvider` выбирает Claude или Codex по текущим настройкам. `AiActionTools` задаёт инструменты действия и путь состояния для MCP. Создание героя и старт используют черновик; обычные ходы — активное сохранение.

Мастер возвращает JSON с патчами и `history`. `SequentialHistoryPlayer` применяет корневой патч, затем последовательно показывает записи, анимирует `movePath` и применяет вложенные `patch`. Броски, реакции и выбор цели проходят через MCP и файловые запросы к UI; старый маркер `triggerReaction` не является текущим протоколом.

`Speech` озвучивает новые записи истории и реплики MCP через локальный Silero в отдельной ограниченной очереди. Синтез и аудио не блокируют UI; Enter, Esc и F11 отменяют текущую речь и очередь. Настройки включения, громкости, голоса и пути Python сохраняются только у игрока. Готовая сборка содержит переносимый Python, CPU PyTorch и модель в `Speech/silero/`: скачивание при включении не требуется. Комплект готовит `prepare-silero-bundle.ps1`; личные файлы из Storage не копируются. При запуске из исходников без комплекта сохраняется установка в `Storage/Speech/silero/` через `setup-silero.ps1`. Озвучка по умолчанию выключена. `SileroSpeech` управляет Python-процессом через JSON-lines: `silero_worker.py` загружает модель один раз и создаёт WAV для каждой реплики. Отмена во время синтеза завершает процесс; следующая реплика загрузит его заново.

## Состояние и патчи

`history[].text` может содержать SSML `<speak>`. `Speech.DisplayText` готовит обычный экранный текст, сохраняя механику в `[...]`; `Speech.ValidateSsml` оставляет разрешённую разметку и исключает механику из озвучки. `DialogMessage.SpeechText` — локальная производная копия для речи, не отдельное поле ответа модели. Преобразование выполняется в `Storage.ApplyUpdateWorldState`, `SequentialHistoryPlayer` и потоке MCP-истории. `AiContextBuilder` возвращает модели только очищенную историю. `Speech.Initialize` заранее ставит в очередь тихий прогрев Silero, не блокируя меню.

`WorldState` хранит героя, карту, историю, время, бой, сюжет и связь с миром. `CellEntity` задаёт объект карты, `LivingEntity` добавляет хиты и эффекты, `Hero` — характеристики, ресурсы, действия и снаряжение. JSON использует camelCase; чтение регистронезависимое.

`Storage.ApplyUpdateWorldState` применяет изменения. Для коллекций с `PatchByIndex`:

- `id` — индекс текущего списка; без `id` элемент добавляется.
- Существующий индекс обновляет только переданные поля; новый индекс добавляет элемент.
- `deleted: true` удаляет элемент, если коллекция допускает удаление; удаления выполняются с конца списка.
- Механизм используется для характеристик и ресурсов героя, комнат, существ и объектов. Устаревшее правило «заменить эти списки целиком» неверно.
- Изображения обновляются по `key`. Остальные поля обрабатываются своими `Apply*`; точный контракт находится в `Storage.cs` и промптах.

Координаты тактической карты — `[col, row]`, начиная с 1; символы сущностей — три знака. Для патчей по индексам мастер получает данные через `get_world_state`; ключи и фильтры определяются `WorldStateTools` и `AiContextBuilder.Serialize`.

## Опыт и уровни

`hero.level` и `hero.xp` ведёт движок: из ответа мастера они не применяются, только из сохранения (`Storage.ApplySavedState` — загрузка, MCP, герой библиотеки). Мастер начисляет опыт патчем `hero.xpAward` (`monsters` — `monsterKey` побеждённых, опыт по уровню опасности; `xp` — за прочее); итог и «доступен новый уровень» движок пишет в историю после ответа. Таблица правил — `GameData/DnD5e_levels.json` (`LevelRules`): пороги, бонус мастерства, кости хитов, уровни улучшения характеристик. Стат «Класс» — без уровня (`ClassLevel` отрезает «3 ур»).

«Новый уровень» (`LevelUpDisplay`, F10 или кнопка на карточке, вне боя) — панель на вкладке «Персонаж» вместо диалога: карточка сверху показывает героя после повышения (`HeroDisplay.Preview`, изменения золотым), в блоке картинки — карточка заклинания из справочника или описание пункта. Свободного ввода в лист нет: код считает хиты (среднее или один бросок), бонус мастерства и улучшение характеристик; `LevelUpOptions` возвращает полученное и группы выбора, строка ввода — просьба о своём варианте (тот же промпт, только по правилам класса и уровня, вариант «★» или отказ); `LevelUpApply` — патч листа по выбору. `LevelUp.Apply` собирает нового героя на копии: из патча — только статы, навыки, умения, ресурсы, заклинания, поверх — числа движка. «Принять» заменяет героя, отмена ничего не меняет. Варианты мастера и бросок хитов хранятся в сохранении (`hero.levelUpDraft`, только движок): отмена, выход в меню и перезапуск не запрашивают их заново и не дают перебросить хиты.

## Карты и время

Локации строятся блоками: мастер задаёт план через `plan_location`, геометрию строит код, следующие блоки наполняет `PopulateChunk`. Есть подземелья, пещеры и открытая местность. Без локации F1 недоступна, игра продолжается на карте мира или в описательной сцене.

`WorldLibrary` хранит геометрию и хронику мира. `GameWorld` связывает её со знаниями героя. `TravelService` рассчитывает путь, время и встречи; мастер получает сводку. Подробнее: [world-map.md](world-map.md).

`TakeRoundBundle` объединяет эффекты и события начала раунда. Боевые перемещения рассчитывает `calculate_movement`, решения врагов принимает мастер. Правила боя находятся в `SendAction/systemPrompt.md`.

## Файлы

- `NaviDnD/Prompts/{RuleSet}/{Action}/systemPrompt.md` — инструкции мастера.
- `GameData`, `icons`, `NaviDnD/sound`, `NaviDnD/Fonts` — ресурсы приложения.
- `NaviDnD/Storage/settings.json` — настройки; `gameN.json` — сохранения; рядом — туман войны и заметки.
- `Storage/Worlds`, `Heroes`, `Portraits` — личные библиотеки; `logs` — диагностика. Всё это исключено из Git.

Каталоги и настройки создаются при первом запуске; остальные данные — по мере использования. Пустой запуск не создаёт фиктивную сохранённую игру. Миграция старых сохранений сохранена.

`AppConfig.ProjectRoot` определяется по текущей сборке: при запуске из исходников данные находятся в игровом проекте, при тестировании логики — в тестовом. Настройки Codex: [codex.md](codex.md). Проверки: [testing.md](testing.md).
